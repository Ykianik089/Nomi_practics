# Спецификация протокола Nomi v1

Транспорт — **UDP**. Одна команда = одна датаграмма, порядок байт — **little-endian**
(преобразования выполняются явно через `BinaryPrimitives`, поэтому протокол не зависит
от платформы).

Датаграмма = заголовок (12 байт) + полезная нагрузка (0…65535 байт).
Реальный размер нагрузки в этой работе не превышает 20 байт, что заведомо меньше MTU,
поэтому фрагментации на уровне IP не происходит.

## 1. Заголовок пакета

| Смещение | Размер | Поле          | Тип      | Описание                                       |
|---------:|-------:|---------------|----------|------------------------------------------------|
| 0        | 1      | `Version`     | `uint8`  | версия протокола, сейчас `1`                   |
| 1        | 1      | `Type`        | `uint8`  | тип команды, см. §2                            |
| 2        | 2      | `Sequence`    | `uint16` | порядковый номер пакета у отправителя          |
| 4        | 2      | `PayloadSize` | `uint16` | размер полезной нагрузки в байтах              |
| 6        | 2      | `Reserved`    | `uint16` | резерв (нули), выравнивание до 4 байт          |
| 8        | 4      | `Checksum`    | `uint32` | CRC32 полезной нагрузки (полином `0xEDB88320`) |

Получатель обязан проверить в таком порядке: длину датаграммы → `Version` → соответствие
`PayloadSize` фактической длине → `Checksum`. Любое несовпадение — пакет отбрасывается
и пишется в лог.

## 2. Типы команд (`PacketType`)

| Код | Имя               | Направление     | Нагрузка                 | Смысл                               |
|----:|-------------------|-----------------|--------------------------|-------------------------------------|
| 1   | `CONNECT`         | клиент → сервер | `ConnectPayload`         | рукопожатие, имя пользователя       |
| 2   | `CONNECT_ACK`     | сервер → клиент | `StatePayload`           | пользователь принят, выдан id       |
| 3   | `DISCONNECT`      | клиент → сервер | пусто                    | корректный выход                    |
| 9   | `ERROR`           | сервер → клиент | UTF-8 текст              | пакет отвергнут, причина текстом    |
| 10  | `LOCATION_UPDATE` | клиент → сервер | `LocationPayload`        | текущие GPS-координаты              |
| 11  | `REACTION`        | клиент → сервер | `ReactionPayload`        | эмодзи-реакция другому пользователю |
| 20  | `STATE_UPDATE`    | сервер → клиент | `StatePayload`           | подтверждение координат и состояния |
| 21  | `REACTION_RESULT` | сервер → клиент | `ReactionResultPayload`  | результат доставки реакции          |

Коды 12–16 зарезервированы под механики следующих практик: `CHECK_IN`, `SEND_MESSAGE`,
`CREATE_MARK`, `STATUS_UPDATE`, `ROUTE_REQUEST`.

## 3. Полезные нагрузки

### 3.1 `CONNECT` — `ConnectPayload` (1 + N байт)

| Смещение | Размер | Поле         | Тип      | Описание                   |
|---------:|-------:|--------------|----------|----------------------------|
| 0        | 1      | `NameLength` | `uint8`  | длина имени в байтах, ≤ 32 |
| 1        | N      | `Name`       | UTF-8    | имя пользователя           |

### 3.2 `LOCATION_UPDATE` — `LocationPayload` (12 байт)

| Смещение | Размер | Поле  | Тип     | Описание                     |
|---------:|-------:|-------|---------|------------------------------|
| 0        | 4      | `Lat` | `float` | широта, градусы (-90…+90)    |
| 4        | 4      | `Lng` | `float` | долгота, градусы (-180…+180) |
| 8        | 4      | `Alt` | `float` | высота, метры (-100…+9000)   |

Клиент передаёт **текущую позицию**, сервер её валидирует: обрезает по допустимым
диапазонам и отбрасывает, если шаг от прошлой позиции превышает 500 м (защита от
подмены координат и «телепортов»).

### 3.3 `REACTION` — `ReactionPayload` (5 байт)

| Смещение | Размер | Поле        | Тип      | Описание                               |
|---------:|-------:|-------------|----------|----------------------------------------|
| 0        | 1      | `EmojiId`   | `uint8`  | 1 — 👋, 2 — ❤️, 3 — 😂, 4 — 🔥, 5 — 👀 |
| 1        | 4      | `TargetUid` | `uint32` | id получателя                          |

Кулдаун между реакциями — 1000 мс. Если получатель офлайн/не найден — сервер
возвращает `REACTION_RESULT` с `Delivered = 0`.

### 3.4 `CONNECT_ACK` / `STATE_UPDATE` — `StatePayload` (20 байт)

| Смещение | Размер | Поле          | Тип      | Описание                            |
|---------:|-------:|---------------|----------|-------------------------------------|
| 0        | 2      | `UserId`      | `uint16` | идентификатор пользователя          |
| 2        | 4      | `Lat`         | `float`  | текущая широта                      |
| 6        | 4      | `Lng`         | `float`  | текущая долгота                     |
| 10       | 4      | `Alt`         | `float`  | текущая высота                      |
| 14       | 1      | `Status`      | `uint8`  | 1 — онлайн, 2 — невидимка           |
| 15       | 1      | `Reserved`    | `uint8`  | резерв (нули)                       |
| 16       | 2      | `AckSequence` | `uint16` | номер команды, на которую это ответ |
| 18       | 2      | `Reserved`    | `uint16` | резерв (нули)                       |

### 3.5 `REACTION_RESULT` — `ReactionResultPayload` (7 байт)

| Смещение | Размер | Поле          | Тип      | Описание                              |
|---------:|-------:|---------------|----------|---------------------------------------|
| 0        | 2      | `UserId`      | `uint16` | кто отправил реакцию                  |
| 2        | 1      | `EmojiId`     | `uint8`  | какую реакцию отправил                |
| 3        | 1      | `Delivered`   | `uint8`  | 0 — не доставлено, 1 — доставлено     |
| 4        | 2      | `AckSequence` | `uint16` | номер обработанной команды `REACTION` |
| 6        | 1      | `Reserved`    | `uint8`  | резерв (нули)                         |

### 3.6 `ERROR`

Полезная нагрузка — текст причины в UTF-8, без завершающего нуля.

## 4. Сценарий обмена

```
клиент                                   сервер
  |  CONNECT      seq=1  «Nomi»             |   регистрирует пользователя, пишет в лог
  | --------------------------------------> |
  |  CONNECT_ACK  id=1, lat/lng/alt         |
  | <-------------------------------------- |
  |                                         |
  |  LOCATION_UPDATE seq=2 (lat,lng,alt)    |   проверяет CRC, seq, шаг и границы
  | --------------------------------------> |
  |  STATE_UPDATE ack=2, новая позиция      |
  | <-------------------------------------- |
  |                                         |
  |  REACTION     seq=3 (эмодзи, targetUid) |   проверяет кулдаун и наличие получателя
  | --------------------------------------> |
  |  REACTION_RESULT ack=3, delivered=1     |
  | <-------------------------------------- |
  |                                         |
  |  DISCONNECT   seq=N                     |   удаляет пользователя из таблицы
  | --------------------------------------> |
```

## 5. Порядковые номера и надёжность

* `Sequence` — отдельный счётчик у клиента и у сервера, начинается с 1, растёт на каждый
  отправленный пакет, при переполнении `uint16` обнуляется.
* Сервер хранит номер последнего принятого пакета пользователя. Пакет с `Sequence`
  не больше сохранённого считается дубликатом или «опоздавшим»: к состоянию он не применяется,
  в ответ уходит текущее `STATE_UPDATE`.
* Ответ сервера содержит `AckSequence` — подтверждение конкретной команды.
* Повтор реализован только для рукопожатия (`CONNECT` — до 5 попыток по 1 с). Команды
  `LOCATION_UPDATE`/`REACTION` не переотправляются: они устаревают быстрее, чем дойдёт повтор,
  — стандартный подход для потоковых геосоциальных приложений.

## 6. Ограничения текущей версии

* Сервер отвечает только тому клиенту, который прислал команду; рассылка координат всех
  друзей (broadcast) появится в следующих практиках.
* Нет аутентификации и шифрования.
* Реакции не доставляются офлайн-получателям — только подтверждается факт.
