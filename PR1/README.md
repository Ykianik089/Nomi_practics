# Практическая работа №1 — UDP-протокол и архитектура Nomi

## О чём эта работа

Первая практика по проектированию клиент-серверных систем. Цель — заложить
фундамент сетевого взаимодействия для сквозного проекта **Nomi** — мобильного
геосоциального приложения (клон Blink/Zenly), в котором пользователи видят
друг друга на карте в реальном времени и обмениваются эмодзи-реакциями.

В рамках работы мы:
- выбрали топологию сети и обосновали её;
- разработали собственный бинарный протокол обмена;
- реализовали **UDP-сервер** и **UDP-клиент** на C#;
- заложили основу для дальнейших практик (чат, чекины, маршруты, метки).

## Что мы сделали

### 1. Выбрали топологию — Dedicated Server

Клиенты не общаются друг с другом напрямую (P2P), все данные идут через
центральный сервер. Причины:
- **Авторитетный сервер** — координаты нельзя доверять клиентам (защита от
  подмены геопозиции).
- **Масштабируемость** — P2P плохо работает при большом числе пользователей.
- **Мобильные клиенты** — у телефонов меняется IP, прямое соединение ненадёжно.
- **Допустимая задержка** — 50–200 мс приемлемо для геосоциального приложения.

### 2. Спроектировали бинарный протокол

Датаграмма = **заголовок (12 байт) + полезная нагрузка (0…65535 байт)**.

Заголовок:
| Поле | Размер | Назначение |
|---|---|---|
| Version | 1 байт | версия протокола |
| Type | 1 байт | тип команды |
| Sequence | 2 байта | порядковый номер |
| PayloadSize | 2 байта | размер полезной нагрузки |
| Reserved | 2 байта | выравнивание |
| Checksum | 4 байта | CRC32 полезной нагрузки |

Поддерживаемые команды:
- `CONNECT` / `CONNECT_ACK` — рукопожатие, представление пользователя.
- `LOCATION_UPDATE` — передача GPS-координат (широта, долгота, высота).
- `REACTION` — эмодзи-реакция другому пользователю.
- `STATE_UPDATE` — подтверждение координат и текущего состояния.
- `REACTION_RESULT` — результат доставки реакции.
- `DISCONNECT` — корректный выход.
- `ERROR` — текстовая причина отказа.

Полная спецификация — в [docs/Protocol_Specification.md](docs/Protocol_Specification.md).

### 3. Реализовали UDP-сервер (`src/Nomi.Server`)

Функции сервера:
- слушает UDP-порт, принимает датаграммы;
- проверяет пакет: длину → версию → `PayloadSize` → CRC32;
- ведёт таблицу подключённых пользователей (`id`, координаты, статус);
- валидирует координаты: широта ±90, долгота ±180, высота −100…+9000;
- **анти-чит по шагу** — если расстояние от прошлой позиции > 500 м, координата
  отклоняется (защита от телепортов);
- обрабатывает эмодзи-реакции с кулдауном 1000 мс и проверкой получателя;
- **логирует все команды** в консоль и в файл `logs/server-ГГГГ-ММ-ДД.log`.

### 4. Реализовали UDP-клиент (`src/Nomi.Client`)

Функции клиента:
- выполняет рукопожатие (`CONNECT` → `CONNECT_ACK`) с 5 попытками по 1 секунде;
- раз в секунду шлёт по очереди `LOCATION_UPDATE` и `REACTION`;
- принимает ответы сервера и печатает их;
- корректно завершается по `Ctrl+C`, отправляя `DISCONNECT`.

### 5. Заложили основу для следующих практик

В `PacketType` зарезервированы коды 12–16 под механики Nomi:
`CHECK_IN`, `SEND_MESSAGE`, `CREATE_MARK`, `STATUS_UPDATE`, `ROUTE_REQUEST`.
В заголовке есть поле `Reserved` для расширения без смены версии протокола.
